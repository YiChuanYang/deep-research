# RAG 提速与设备配置

本轮优化分为本地检索计算和重排输出两部分。网页数量、候选数、证据数量和反思轮数没有作为提速手段缩减。

已验证的设备、耗时、评分变化及测试边界见 [本轮实测结果](rag-speed-results.md)。

## 检索链路

```text
搜索引擎发现网页 → 提取正文 → 分块
                              ├─ BM25：词项匹配与排名 ───┐
                              └─ Embedding + 余弦排名 ─┤
                                                       ↓
                                             RRF 按名次融合
                                                       ↓
                                          取最多 16 个候选
                                                       ↓
                                        远程 LLM 重排（0～3）
                                                       ↓
                                 过滤低相关、去重、限制来源和长度
                                                       ↓
                                            最多 8 个证据片段
```

上图表示两路召回的逻辑关系，不表示本轮已经实现并行执行。

- **BM25** 用分词后的查询匹配正文。词频、词在语料中的稀有程度和文档长度共同影响分数，适合专有名词、代码和精确术语。它不调用大模型，不生成文本。
- **向量检索** 将查询与片段编码成向量，按余弦相似度排序，补充关键词不同但意思相近的内容。正文向量可预先算好；每个新查询只需编码查询本身。标题、条件或否定词不同的文本也可能相似，语义接近不代表能回答问题。
- **RRF** 合并两路名次。本项目每路贡献为 `1 / (60 + rank)`，不直接把 BM25 分数和余弦分数相加。每路最多参与前 `candidates * 2` 项，然后选择融合后的候选。
- **Reranker** 再次阅读完整问题和少量候选，检查实体、版本、条件等相关性。本项目使用远程智谱聊天模型做列表评分，不是本地专用 Cross-Encoder。0 表示无关，1 仅背景，2 部分回答，3 直接回答；低于 2 的候选不进入证据。

例如查询“进程崩溃后怎样避免通知重复发送”：BM25 可能找到含“崩溃、通知、重复”的片段；向量检索可能补充“幂等键、至少一次投递、持久化发送意图”的片段；重排进一步区分网页讲的是消息通知还是手机通知设置。这个例子只说明分工，不意味着模型一定判断正确。重排仍不能证明来源权威或报告结论正确。

## 本轮改动

1. 分词结果以不可变 tuple 缓存，最多保留 4096 项；每份研究复用最近一次 BM25。语料内容、标题或顺序变化时重建，避免 IDF 使用过期语料。
2. 查询向量按模型签名和完整查询保存，和正文向量使用不同的缓存键。同一研究的本地查找与联网补查可以复用；切换模型不会误用旧向量。
3. 同批重复正文只编码一次；相同网页快照和分块参数可复用分块。既有正文向量键和证据快照保持兼容。
4. SQLite 在 SQL 中筛选所需网页和片段；向量每 400 个键批量读取，维持原有稳定顺序。向量相似度使用批量矩阵计算。
5. 重排默认只输出 `id` 和 `score`，保留完整编号、重复编号、分数范围校验和一次格式修复。调试开关可恢复逐项理由。旧研究恢复时保留原有理由模式。
6. 记录 RAG 内部分步耗时、查询和 BM25 缓存命中、新编码数、设备与真实 ONNX 执行器。评测汇总展示 `rag_steps`；这部分包含在图节点耗时中，不能重复相加。

## GPU 为什么需要额外配置

安装显卡驱动不代表 Python 中的推理运行时支持 CUDA。此次检查机器是 NVIDIA GTX 1650 Ti 4GB，原环境安装 CPU 版 `onnxruntime`，只提供 CPU/Azure 执行器，因此 FastEmbed 一直使用 CPU。

Windows 依赖现在使用 `fastembed-gpu` 与 CUDA 12 系列 `onnxruntime-gpu`，CUDA/cuDNN DLL 也由 uv 安装到项目环境。CPU/GPU 两套同名 ONNX 模块不同时安装。其他系统仍使用原 CPU 包。无需修改系统显卡驱动或安装完整 CUDA Toolkit。Windows GPU 运行时本身也提供 CPU 执行器。

初始化会调用 ONNX Runtime 的 `preload_dlls` 加载项目环境里的运行库，并核对模型会话实际启用的 providers；只看驱动或 `get_available_providers()` 不足以确认会话成功。部分形状处理等算子可能仍由 CPU 执行。

参考：[ONNX Runtime CUDA 执行器与运行库说明](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)。

## 可配置项

以下是默认值，可在 `backend/.env` 覆盖：

```dotenv
EMBEDDING_DEVICE=auto
EMBEDDING_THREADS=2
EMBEDDING_BATCH_SIZE=16
RERANK_INCLUDE_REASON=false
```

- `auto`：优先尝试 CUDA 会话，初始化失败时记录原因并使用 CPU。
- `cuda`：要求 CUDA 会话成功；失败抛错，由原检索流程记录向量不可用并降级，不伪装成 GPU 成功。
- `cpu`：明确使用 CPU，方便回归与设备对照。
- `threads` 控制本地 ONNX 会话 CPU 线程数，不是同时执行多少研究任务。
- `batch_size` 控制一次编码的文本数量，显存较小时应保守设置。GPU 不保证所有批量和短查询都快，需在实际文本上测量。
- `rerank_include_reason=true` 返回评分理由，便于排查语义筛选；`false` 缩短生成文本。两种模式可能产生不同评分，不应承诺排序完全一致。

本机 GPU 主要用于 Embedding 编码；BM25、SQLite、小规模向量分数计算仍在 CPU。摘要、报告和当前重排调用远程接口，本机 GPU 不能加速远端模型推理。

从 backend 目录执行 `uv sync` 同步依赖，随后按原有方式启动应用。首次 GPU 运行库下载较大；后续无需重复下载。日志中应看到 `⚡ rag.embed` 的实际 device。

## 验证方法

局部测试脚本只读旧批次网页，并在新目录保存基准结果，避免污染原评测材料。

```powershell
# 离线比较 CPU/GPU、分批大小和 BM25 缓存。
uv run python -m evals.benchmark_rag evals/runs/20261116T153227Z-e085d741 --devices cpu cuda --batch-sizes 16 --chunks 64 --repeats 3

# 实际调用当前模型，对同一组候选比较带理由与精简输出；交替执行顺序。
uv run python -m evals.benchmark_rag evals/runs/20261116T153227Z-e085d741 --case-id DR-002 --rerank --repeats 2
```

分别查看模型加载、预热后编码、缓存命中和重排修复成本。局部基准不等于端到端研究提速，也不能替代报告质量评测。整条研究的收益应在相同题集和冷/热缓存条件下另行测量。
