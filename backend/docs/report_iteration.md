# 报告反思、定向补搜与报告修订

## 功能与边界

建立在 query-rewrite-citation-v2 上。初始任务仍使用查询改写、搜索、证据登记、摘要和笔记保存；报告草稿完成后才进入独立的 `reflect_report` 节点。没有恢复之前的任务摘要反思或证据语义筛选模块。

```text
plan → select_task → rewrite_query → search → summarize → save_note
          ↑                                                 │
          └─────────────────────────────────────────────────┘
          │ 无待执行任务
          ↓
        report（只保存草稿）→ reflect_report
                                ├─ 无问题 → finalize_report → save_report → END
                                ├─ 缺材料 → prepare_report_revision → select_task
                                ├─ 已有材料可修订 → prepare_report_revision → report
                                ├─ 非关键缺口且停止 → finalize_report（有限交付）
                                └─ 仍有实质问题 → block_report（保留草稿，不发布）
```

评审通过只表示模型本次没有提出问题，不表示外部事实已被证实。内容质量需要独立人工评测；协议、引用结构和图运行成功率不能代替质量分。

## 模块职责

| 文件 | 负责什么 |
|---|---|
| `report_iteration.py` | 评审问题、草稿、补充任务记录、集中保存的迭代状态 |
| `services/report_reflection.py` | 原生结果工具调用、完整材料输入、协议及证据编号校验、一次协议修复 |
| `graph/report_cycle.py` | 确定性决策、预算、问题与查询去重、追加任务、判断停机 |
| `graph/graph_nodes.py` | 调用服务、更新业务字段、产生事件、连接图节点 |
| `services/reporter.py` | 根据摘要、证据、旧报告和反馈生成整版正文 |
| `services/report_format.py` | 程序附加的任务范围和报告复核说明，评测共用 |

模型不会自行调用搜索工具、修改状态或写文件。它只提交问题，程序根据问题种类和剩余预算决定下一步。

## 一次补充研究的数据流

1. 初始任务完成后，Reporter 返回引用已校验的 `CitedText`。本功能开启时返回纯正文，正式引用附录等到定稿才添加。
2. `report` 节点把正文、实际引用和 revision 保存进图的 `report_iteration.drafts`。此时 `SummaryState.structured_report` 仍为空。
3. 评审服务把正文按空行切成有稳定 P 编号的段落。输入包括主题、所有任务的目标和状态、已完成摘要，以及这些摘要实际引用的证据。这样可以发现“已有研究结果没写进报告”。
4. 模型返回 `revisions`（最多两项）和 `research_gaps`（最多一项）。程序将它们转换为原来的 `issues` 持久化结构。`revisions` 只有问题类型、说明、段落编号和证据编号；`research_gaps` 包含说明、原问题片段 `topic_quote`、领域研究问题和查询。原问题片段必须能在用户主题中逐字找到；两种动作的参数不能混填。
5. `reflect_report` 将结果绑定到这版草稿，提交检查点。普通语义评审和协议修复是两种预算，分别保存。
6. `prepare_report_revision` 对缺口和查询去重，检查明显的“报告是否提及”自评问题，分配新任务编号。任务目标只包含研究问题；评审理由保留在迭代审计中，不作为摘要的事实前提。每轮最多追加一个任务。查询改写和搜索入口也执行边界检查，覆盖直接恢复到搜索的情况。
7. 新任务继续走现有任务链。它获得的新 E 编号进入全研究累计证据目录；原任务、原证据和原编号保留。补充摘要只接收领域问题与编号证据；返回明确的报告自评语句时整段拒绝，转为资料不足并跳过该任务，不进入报告引用范围。
8. 补充摘要完成后，Reporter 输入全部已完成摘要、对应证据、上一版报告和反馈，生成完整的新正文。新材料只有进入已完成摘要的引用范围后才可用于报告。
   评审和修订共用 `report_paragraphs()` 生成的段落字典，例如 `{"P0002": "原报告的某一段"}`。这样反馈中的 `paragraph_id` 能定位回原文；P 编号不会要求模型写进正式报告。
9. 新草稿再评审。达到交付条件后，`finalize_report` 写正式报告与复核说明，`save_report` 保存笔记后设置图顶层 `finished=True`。

初始 `max_tasks` 只限制初始任务。调度与 API 统一从迭代记录中的 `initial_task_ids` 加补充任务编号取得实际执行集合，所以初始上限为 2 时，补充任务 4 仍可执行。没有被选中的初始任务不会因为追加任务而意外执行。

## 状态和恢复

业务对象继续使用 `TodoItem`、`Source`、`Evidence`、`CitedText`。图增加一个可缺省的 `report_iteration` 字典。`SummaryState` 只增加 `report_limitations`，用于最终报告的可持久化交付说明，不保存循环控制字段。

`ReportIteration` 集中记录：初始执行任务编号、补充任务及原因、新材料编号、当前 revision、各版草稿及评审、协议修复次数、下一动作和停止原因。

这里使用 Pydantic：`model_validate()` 将普通字典校验并还原为对象，`model_dump(mode="json")` 返回可写入检查点的普通字典，`model_json_schema()` 生成原生结果工具的参数结构。`Field(default_factory=list)` 为每个对象创建独立列表；`model_validator(mode="after")` 在字段校验后检查问题类型与参数是否一致。

部分兼容接口不能可靠理解 JSON Schema 的 `$defs/$ref`（把公共结构放在定义区，再按路径引用）。发送工具参数前，`review_schema()` 将本模型已知的这一层引用展开成完整结构，并在提示词中说明结果示例。即使提供商把结果写进普通正文，也必须通过相同的 JSON 和 Pydantic 校验，不猜测缺失字段。

图的 `TypedDict(total=False)` 让旧检查点允许没有新增字段。旧配置快照缺少 `enable_report_reflection` 时按 false 恢复，保持原 v2 拓扑；新研究的开关、轮次上限和补充预算会冻结进配置快照。

| 中断位置 | 恢复行为 |
|---|---|
| 补充搜索失败 | 重试同一补充任务，既有任务和已提交的补充任务编号不重建 |
| 报告修订失败 | 保留上一版草稿与已完成补充研究，只重试报告节点 |
| 评审中的程序/鉴权异常 | 继续报错，保留当前草稿，修复后可恢复 |
| 最终笔记保存失败 | 只重试 save_report，不重新生成和评审 |
| 预算耗尽且仍有实质问题 | 停在 block_report，草稿可查，API 拒绝无意义地再次续跑 |

节点未提交就崩溃时，外部模型或搜索调用可能在恢复时重复；预算限制针对成功提交的业务轮次，不承诺外部请求恰好一次。SDK 的网络重试仍使用现有配置。

## 停止与交付规则

| 状态 | 具体行为 |
|---|---|
| accepted | 最新一版有有效评审，且 issues 为空；正常交付 |
| limited | 剩余问题只有覆盖/遗漏等非阻断项，达到预算、查询重复或无进展；交付并列明不足 |
| unreviewed | 评审格式修复失败、材料超过预算或暂时性连接/限流故障，且历史没有已知实质问题；明确标注未复核 |
| blocked | 最新评审仍指出无依据/矛盾，或已有实质问题但新的复核失败；保存草稿，不生成正式报告 |

所有候选报告先通过引用编号和范围校验。鉴权错误、未知程序错误、数据库与笔记写入失败不被当作语义问题吞掉。

同一份正文再次生成时复用其已绑定的评审并停止重复循环。`comparable_report()` 忽略代码围栏外的空行和行尾空格，保留行内空格、换行顺序、缩进及围栏内代码；不删除全部空白后比较。复用反馈会记录 `review_reused_from`，前端标明来源版本，因为空行变化可能改变 P 编号。跨任务新材料判断仍使用空白归一化后的文本 SHA-256；这不是语义去重。

一次补搜没有取得内容不同的新材料后，不再继续补搜，但仍允许在剩余预算内利用已有材料修订。原查询和改写后的实际查询都会检查重复。

报告评审输入超过 `report_review_max_chars` 时不调用评审模型，记录未复核原因；不会把截断材料后的判断冒充全文核查。这个预算是业务输入 JSON 的字符数，不是模型 token 数。

## 配置与成本

默认启用，新研究使用：

```dotenv
ENABLE_REPORT_REFLECTION=true
REPORT_MAX_REVISIONS=2
REPORT_MAX_SUPPLEMENT_TASKS=2
REPORT_REVIEW_MAX_CHARS=60000
```

初稿 revision=0，最多两轮额外改进，所以最多三版报告；一轮只改写报告也消耗一次改进预算。全研究最多两个补充任务、一次协议修复。当前配置允许将改进/补充上限设置为 0～3。

两轮都补搜时，通常最多新增九次逻辑模型调用：初稿评审一次，每轮查询改写、补充摘要、报告修订、再评审各一次，另增加两次搜索。协议修复最多再增加一次模型请求；SDK 重试和故障后的手动恢复不在这个逻辑次数中。字符预算、生成长度和证据数量都会影响真实 token 消耗。

## 前端和接口

状态接口新增 `report_iteration` 概览，包含版本、改进上限、初始/补充任务计数、交付状态和问题数。普通轮询不传输草稿全文。

`GET /api/research/{run_id}/iterations` 返回已提交的各版草稿、评审结果、补充任务及取得的新材料编号。前端展开“查看草稿与补充记录”时才读取此资源。

每次报告流仍有独立的 generation_id，前端不会把新版分片接到旧稿后面。正式结果接口仍以 report_ready 为准。blocked 时可以读取草稿，但不能下载或获取正式报告。

新增日志沿用表情与分栏：`🪞 services.review` 展示报告核对，`🔄 graph.report_cycle` 展示定向补充和修订。新增节点的控制台阶段使用短中文，JSON 日志保留原节点名。

## 演示和验证

在 backend 下运行真实演示，使用现有 .env 凭证：

```powershell
uv run python -m demo.demo_report_iteration
uv run python -m demo.demo_report_iteration --topic "你的主题" --max-tasks 2
```

失败和成功都会打印 run_id；`data/diagnostics/report-iteration-*` 中保存日志、状态、iterations.json 和用量，成功时另存报告及自动引用检查。

离线主线回归：

```powershell
uv run python -m pytest tests/test_report_boundaries.py tests/test_report_iteration.py tests/test_query_rewriting.py tests/test_citation_normalization.py tests/test_streaming.py tests/test_evals.py tests/test_v2_rollback.py tests/test_utils.py tests/test_tools -q
```

原有手写工作流的日志/笔记测试仍有历史接口不兼容；不要将以上主线回归表述为全仓库 pytest 通过。

评测批次新增 `report_iterations.json`（含失败研究已提交的草稿），telemetry 和 summary 记录评审、协议修复、补充任务、纯改写及交付事件。原人工质量评分公式不变。对照 v2 时用 `ENABLE_REPORT_REFLECTION=false` 跑基线，保持题集、模型、搜索和其他配置一致；版本标签本身不会切换代码。

此前一次真实运行暴露当前模型对嵌套工具 Schema 的兼容问题，协议修复也未成功，按 `unreviewed` 交付。展开 Schema 并明确结果示例后，同材料探测和上述完整研究均能返回有效评审。

## 已记录问题与边界修复

后续高光谱分类研究 `67669d9717bd49a694eee4a6cd367350` 完成三个初始任务、一个补充任务，保留 20 条证据，最终以 `unreviewed` 交付。它暴露了以下问题（下面描述故障时的旧行为）：

- 评审将正文已包含的 FCN 内容判为遗漏；反馈的语义正确性没有得到保证。
- `question` 可以是“报告是否提及某内容”，随后被直接转为网络研究任务。补充摘要把反馈照抄为结论并附上外部证据编号，引用结构校验无法识别这种语义错配。
- 两版正文只相差六个换行符。当前 `.strip()` 比较只忽略首尾空白，漏掉了正文内部空行变化，未能停止无实质进展的修订。
- 第二版评审同时返回 `omission` 和补搜参数，一次协议修复后仍不合法。程序按现有规则标注未复核，不表示质量通过。

现已将两版正文、原始模型反馈、初始材料和补充摘要冻结在 `tests/fixtures/report_cycle_hyperspectral.json`。边界修复与验证结果见 [报告反思修复记录](report_iteration_fixes.md)。原历史研究不改写，新建研究使用修复后的逻辑。

当前历史评测中的质量评分由 Codex（AI 单评审）填写，不能表述为独立人工验证。新增三题冻结初稿对照用于诊断增量，仍不等于整批独立质量评测。
